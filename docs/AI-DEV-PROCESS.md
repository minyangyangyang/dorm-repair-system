## 1. AI 工具与协作模式

### 1.1 使用的 AI 工具

| 项目 | 说明 |
| --- | --- |
| 工具形态 | 集成在开发环境中的 AI 编程助手（WorkBuddy），具备读取文件、执行命令、检索代码、编辑文件的能力 |
| 能力边界 | 可在本机读取源码、运行测试与 Git 只读命令、创建与修改文件；**不得**在未授权时执行破坏性操作 |
| 模型用途 | 代码与文档的理解、审查、生成；需求对照分析；测试执行与结果归纳；Git 发布方案设计 |

### 1.2 人机协作的基本原则【有据】

本项目采用**"人工决策、AI 执行、人工验收"**的循环，并在任务指令中显式设定约束。以下原则在验收阶段的实际协作中被反复使用，体现在：

1. **先理解、后动手**：AI 先通读 README、源码、测试与 Git 状态，再给出结论，避免在未阅读代码的情况下臆断。
2. **只读优先**：涉及 Git、数据库等不可逆操作时，先执行只读检查（状态、分支、差异、忽略规则），经人工确认后才进入写操作。
3. **禁止无谓重构**：明确要求"优先指出可能影响验收的问题，不要无故重构项目"。
4. **隔离验证**：测试必须使用独立临时数据库，禁止触碰真实业务库。
5. **失败即停**：遇到网络异常、认证错误、非快进冲突时停止操作并汇报，**禁止强制推送、reset、rebase**。

### 1.3 人机分工

| 环节 | 人工（作者） | AI 助手 |
| --- | --- | --- |
| 需求与范围确定 | 主导：确定三角色、功能清单、评分关注点 | 辅助：对照必做要求逐项核查，输出差距清单 |
| 架构与技术选型 | 主导：确定 Vue 3 + Express + SQLite、不引入 ORM/JWT | 辅助：整理既有选型并说明理由 |
| 编码实现 | 主导：代码归属与最终取舍由人工确认 | 执行：按约束生成与修改代码、文档 |
| 测试 | 主导：确定验收标准 | 执行：运行测试并归纳结果，标注覆盖与缺口 |
| 版本发布 | 主导：确认发布方案后才授权执行 | 执行：只读检查、提交、快进合并、推送尝试 |
| 文档撰写 | 主导：确认内容真实性与表述 | 执行：依据源码生成初稿 |

### 2.6 测试阶段【有据】

AI 在本阶段承担了**执行与归纳**工作，测试本身由项目既有用例构成，非临时编造：

| 验证项 | 命令 | 结果 |
| --- | --- | --- |
| 后端测试 | `npm.cmd --prefix backend test` | 59 / 59 通过 |
| 前端请求测试 | `node --test frontend/test/client.test.js` | 8 / 8 通过 |
| 浏览器联调 | `node frontend/scripts/browser-smoke.mjs` | 10 / 10 组流程通过 |
| 前端构建 | `npm.cmd --prefix frontend run build` | 成功（30 个模块） |

- 执行环境：Windows、Node.js v22.22.2、已安装 Chrome 与 Edge。
- **隔离原则**：后端与浏览器测试使用系统临时目录下的独立 SQLite 与临时上传目录，对默认数据库 `backend/data/repairs.sqlite` 仅做只读指纹检查，不写入、不迁移、不重置。
- AI 产出：核对 README 中"59 / 8 / 10"的记录属实，并指出原 README 中"没有重新运行测试"的表述与实际不符，已改为本轮实测结果表。
- 覆盖缺口（AI 明确指出，未隐瞒）：**前端筛选与后端列表分页缺少自动化测试**。

## 3. 本轮（验收阶段）AI 参与工作的实际记录【有据】

以下内容为可查证的完整工作链，对应提交 `d5867e1`（`docs: finalize V2.0 README and gitignore`）：

| 步骤 | AI 执行内容 | 人工决策点 |
| --- | --- | --- |
| 1 | 读取 README、源码、测试与 Git 状态，输出五项必做要求的验收差距清单 | 确认"不修改代码、只报告" |
| 2 | 实跑 59 + 8 + 10 三组测试，核实覆盖率与缺口 | 确认测试必须使用隔离数据库 |
| 3 | 只读检查 `git status` / `branch -vv` / 提交图 / 远程，审计三级 `.gitignore`，核对 README 差异仅删除 2 行占位标题 | 确认发布方案 |
| 4 | 设计"保留全部历史的快进发布方案"，论证采用 `--ff-only` 而非 merge/rebase 的理由 | 人工选择快进方案 |
| 5 | 补全根 `.gitignore`（`.workbuddy/`、`.env`、`.env.*` 并保留 `!.env.example`；`*.sqlite*`；系统杂项） | 人工确认忽略范围 |
| 6 | 修订 README：恢复课程名称副标题、将"已有验证记录"改写为本轮实测结果表 | 人工确认表述 |
| 7 | 提交 `d5867e1` 并 `git merge --ff-only` 快进 `main`，验证两分支指向同一提交 | 人工授权后才提交与合并 |
| 8 | 尝试推送时遇网络阻断（`CONNECT tunnel failed, response 502`、直连超时），**立即停止**，改由 GitHub API 独立确认远端无新提交后汇报失败原因 | 人工在网络恢复后自行完成推送 |
| 9 | 撰写 `docs/DESIGN.md` 与本文档 | 人工核对准确性 |

**关键安全事实**：本轮未使用 `git push --force`、`git reset --hard`、`git rebase`；未删除或重置任何提交；未修改业务代码；未读写或清空真实数据库 `backend/data/repairs.sqlite`；未创建 Tag 或 Release。

## 4. AI 参与带来的质量隐患与人工对策

| 隐患 | 人工对策 | 证据 |
| --- | --- | --- |
| AI 可能生成看似合理但与实现不符的描述 | 文档内容一律回查源码；无法查证处标注【待人工补充】 | 本文档第 0 节的证据边界声明 |
| AI 可能"顺手重构"导致回归 | 任务指令中明确"不要无故重构"，本轮仅改动文档与忽略规则 | 提交 `d5867e1` 仅含 `README.md` 与 `.gitignore` |
| AI 可能误操作数据库或 Git | 任务指令中显式禁止触碰真实数据库、禁止强制推送；先只读检查后写操作 | 第 3 节步骤 3、8 |

## 6. 小结

本项目在验收阶段采用 AI 完成**代码审查、测试执行与结果归纳、发布方案设计与执行、文档撰写**等工作；需求确定、技术选型、代码取舍与最终验收由人工主导。

AI 的介入显著缩短了"通读代码 → 定位差距 → 验证 → 出报告"的周期（本轮全部检查与三组测试在数十分钟内完成），但其产出必须经过**源码回查、测试验证与人工确认**三道关口。对无法查证的内容，本文选择标注缺失而非编造——这既是课程诚信的要求，也是 AI 辅助开发应有的工程态度。
