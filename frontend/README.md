# 宿舍报修管理系统前端

## 工单详情（阶段 6）

学生“我的报修”和维修人员“维修工单”列表均有“查看详情”，点击后在当前工单下展开卡片，点击“关闭详情”或“收起详情”关闭。`src/components/RepairDetails.vue` 直接使用已加载的真实工单，不新增后端 API。

详情展示编号、状态、宿舍楼、房间、类别、描述、联系人、电话、创建和更新时间。API 适配保留 `created_at` / `updated_at` 为 `createdAt` / `updatedAt`，`src/utils/time.js` 将 UTC 时间转换为浏览器本地的中文年月日及时间。PATCH 返回的工单会同步更新详情。

学生已完成工单的详情复用父页面评价缓存，只展示星级、内容和评价时间；尚未评价显示“暂未评价”，查询失败显示错误并引导下方评价区域重试。评价提交仍只使用原有 EvaluationPanel。维修人员详情无评价操作。

人工测试：两端逐条打开核对字段；按状态和类别筛选后打开正确工单；查看已评价和未评价详情；关闭卡片；手机宽度检查长描述及长评价无溢出。状态操作、评价和统计仍使用原有流程。

## 数据统计（阶段 5B）

学生和维修人员顶部导航均有“数据统计”。页面位于 `src/components/StatisticsPage.vue`，通过 `src/api/repairs.js` 的 `getStatistics()` 调用 GET `http://localhost:3000/api/statistics`。统计卡片、状态及类别分布全部使用接口返回的数据，不使用工单列表内存推算，也不预置统计数字。

每次离开再进入统计页面，组件重新挂载并请求最新数据。横向柱状条的宽度 = 当前项数量 / 总工单数 × 100%，类别名称直接使用后端返回的 categoryDistribution。total 为 0 时宽度为 0%，所有零值字段仍显示。完成率直接使用后端返回的 completionRate。

加载时显示“正在加载统计数据……”，失败显示“统计数据加载失败”及中文原因，点击“重新加载”重试。未成功加载不会显示虚构的零值卡片。仅使用 Vue 和 CSS，无新增 npm 依赖。

人工测试：同时运行最新后端和前端，进入统计页面核对数字；提交新工单后重新进入应总数增加。维修人员逐步处理工单后重新进入，各状态和完成率应更新。刷新后再进入仍应读取数据库。停止后端再进入应报错，重启后点击重新加载应恢复。手机宽度查看卡片和柱状条应不溢出。

## 学生维修评价（阶段 4B）

在学生端“我的报修”中，只有已完成工单显示评价区域。`src/components/EvaluationPanel.vue` 查询已有评价，未评价时提供 1～5 星和选填文字（最多 500 字），提交成功后立即显示“已评价”、评分和文字。无评分会提示；提交期间禁用评分、文字、提交和取消按钮。请求失败保留填写内容并显示中文错误。

`src/api/repairs.js` 的 `getEvaluation()` / `submitEvaluation()` 使用现有 fetch 封装和数据库主键调用 GET / POST `/api/repairs/:id/evaluation`。父页面按主键缓存查询结果，正常切换页面或身份不会重复查询；刷新页面重新查询 SQLite，手动重新读取工单列表也会清空缓存。评价查询失败显示“重新读取评价”，不会误显示未评价按钮。

维修人员端不提供评价操作，现有四状态流程不变。评价规则最终仍由后端控制，前端按钮不会绕过未完成或重复评价限制。

人工检查：找一条已完成、未评价工单，点击“评价维修”；不选评分提交应被拒绝。选择 5 星和中文内容提交后应立即显示结果，没有第二次评价按钮。刷新并重启后端后结果应保留。停止后端后提交另一条评价，确认错误提示和填写内容保留。切换维修人员确认无评价区域，手机宽度检查表单和按钮布局。

使用 Vue 3 + Vite，包含学生端和维修人员端演示身份切换。当前工单读取和学生提交已接入 Express + SQLite；维修状态操作也通过 PATCH 保存到 SQLite，刷新或重启后端后仍保留。

## 启动

在项目根目录打开两个 PowerShell 终端：

后端：

```powershell
cd backend
npm.cmd install
npm.cmd start
```

前端：

```powershell
cd frontend
npm.cmd install
npm.cmd run dev
```

后端需要位于 `http://localhost:3000`。前端打开 Vite 在终端显示的地址，通常是 `http://localhost:5173`。已经安装依赖时可跳过 install。

## 数据流程和代码位置

- `src/api/repairs.js` 使用原生 fetch，GET 获取工单，POST 提交六项表单字段，检查响应并转换后端字段。
- `src/App.vue` 的 `onMounted(loadRepairs)` 在页面首次加载及刷新后获取真实记录。两种身份共用 `records`，不再使用预置模拟工单。
- `submit()` 保留前端校验，调用 `createRepair()`，成功后将后端返回的工单放入列表顶部并跳转到“我的报修”。失败时保留表单内容。
- `order_no` 映射为页面显示的 `id`，数据库主键另外存为 `databaseId`；`contact_name`、`contact_phone` 映射为 `contact`、`phone`；`created_at` 转换为浏览器本地时间。
- 查询失败显示中文错误和“重新读取”按钮；提交时禁用表单和提交按钮，避免重复点击。超时设置为 10 秒，不会自动重试 POST。

## 人工测试

状态更新调用位于 `src/api/repairs.js` 的 `updateRepairStatus()`，页面通过 `App.vue` 的 `advanceStatus()` 调用。使用 `databaseId` 发送 PATCH，收到成功响应才替换共享工单；请求失败不修改状态。请求期间禁用状态操作按钮，避免重复点击。

切换维修人员，找一条待处理工单，依次点击接单、开始维修、完成维修。每步应显示中文提示；已完成后不再显示按钮。切换学生或刷新后仍应显示最新状态。重启后端再刷新，确认状态保留。停止后端后操作另一条未完成工单，应显示错误，状态不变化。

1. 同时启动后端和前端，学生进入“我的报修”，确认显示 SQLite 中已有的工单。
2. 提交空表单和错误手机号，确认被阻止。
3. 填写有效内容，提交后确认显示中文成功提示、新编号和“待处理”。
4. 刷新浏览器，重新进入“我的报修”，确认新编号仍然存在。
5. 切换维修人员，进入“维修工单”，确认同一编号、联系人和电话均正确，状态和类别筛选可用。
6. 停止后端并刷新浏览器，确认出现读取失败提示；进入提交页面尝试提交，确认出现提交失败提示且填写内容保留。
7. 重启后端，点击“重新读取”，确认恢复显示。

构建检查：`npm.cmd run build`。本阶段提供状态更新 API，但没有登录或按用户划分工单；演示身份均查看同一份数据库工单。
